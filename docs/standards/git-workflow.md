# Git 工作流规范

本文档细化本项目 `AGENTS.md` 中的 Git 提交与推送规则，适用于人工开发和 AI 辅助开发。

## 核心原则

- 当前仓库默认延续现有工作分支流程；如无特殊说明，当前主线通常在 `main`。
- 每轮任务完成一个稳定可验收的小闭环后，默认应及时 commit 并 push。
- 提交单位不是“消息次数”，而是“最小可解释业务闭环”。
- 提交前只暂存本轮相关文件，禁止默认使用 `git add .`。
- commit 成功后立即推送当前分支，避免本地长期堆积未推送改动。

## 每轮任务开始

开始实际改文件前先执行：

```bash
git status --short
```

目的：

- 识别工作区是否已有历史改动。
- 记录哪些文件不是本轮任务产生的。
- 避免后续提交时把用户、其他任务或历史遗留改动混入本轮 commit。

如果工作区已有未提交改动，仍可继续开发，但必须遵守：

- 不回滚无关改动。
- 不顺手格式化无关文件。
- 不把无关文件混入本轮提交。
- 如果同一文件里混有本轮改动和旧改动，必须逐段检查并只提交本轮意图。
- 无法安全拆分时，暂不提交该文件，并在最终反馈说明原因。

## 每轮完成后的默认提交

用户明确要求实现、修复、调整、完善、联调或继续任务时，视为授权在任务达到稳定可验收状态后提交并推送。

以下泛化回复只表示主线程可继续当前任务，不扩大提交范围：

- “继续”
- “开始吧”
- “可以”
- “按照建议继续”
- “继续处理”

这些回复不授权：

- 把工作区所有未提交改动一起提交。
- 跨任务整理提交。
- 提交未完成或未验证的半成品。
- 提交用户或其他任务留下的无关改动。

## 提交边界

一个 commit 应该能用一句话说明清楚业务目的，并能被单独回滚。

适合单独 commit 的情况：

- 一个 Web 页面交互或样式修复。
- 一个独立知识点场景的可视化改造。
- 一个文档规范补充。
- 一个共享资源目录或品牌资源约定调整。
- 一个小程序页面或配置修复。

可以合并到一个 commit 的情况：

- 同一页面内连续的小样式、小文案、小交互调整。
- 同一模块内为了同一个 bug 必须一起改的测试和实现。
- 同一规范文档和 `AGENTS.md` 中对应的入口说明。

默认需要拆开的情况：

- `web-app/` 与 `wechat-miniprogram/` 两条独立功能改动。
- 业务源码和共享资源母版调整。
- 生成产物和手写逻辑。
- 部署配置和业务功能。
- lockfile 和普通源码。
- 多个互不依赖的功能改动。

## 提交前检查

提交前最低检查：

```bash
git status --short
git diff --check
git diff --cached --check
git diff --cached
```

要求：

- `git diff --check` 和 `git diff --cached --check` 不能有空白错误。
- staged diff 必须逐文件确认，只包含本轮要提交的内容。
- 不使用 `git add .` 作为默认暂存方式。
- 优先使用明确文件路径暂存。

根据改动范围补充验证：

- `web-app/` 改动：至少运行对应的 `npm` 校验命令，如 `npm run typecheck`、`npm run build`。
- `wechat-miniprogram/` 改动：至少检查配置和页面引用关系，必要时在开发者工具中验证页面可打开。
- `ui-design-preview/` 改动：至少本地打开页面检查关键交互和布局。
- 共享文档或规范改动：检查路径引用是否为仓库相对路径，避免失效链接。
- 资源或导出位图改动：确认来源、用途清晰，且不混入临时截图、调试产物或真实敏感信息。

如果因为外部凭证、真实三方环境、端口占用或耗时无法验证，必须在最终反馈中说明。

## 暂存规则

默认使用明确文件路径暂存：

```bash
git add AGENTS.md docs/standards/git-workflow.md
```

对混合改动文件，优先使用交互式暂存或逐段检查：

```bash
git add -p path/to/file
```

禁止：

- 未检查 diff 就 `git add .`
- 把临时截图、浏览器录屏、调试日志顺手提交。
- 把用户或其他任务的文件顺手提交。
- 为了“清空工作区”而提交不属于本轮任务的内容。

## 提交信息

本仓库默认沿用最近历史的 Conventional Commits 风格：

```text
feat(web-app): reshape force lab into exploration workspace
fix(wechat-miniprogram): 修复首页配置引用
docs(standards): 补充 Git 提交工作流规范
refactor(web-app): 拆分可视化页面状态组织
chore(shared-assets): 整理品牌资源说明
```

要求：

- 前缀可用 `feat:`、`fix:`、`docs:`、`test:`、`chore:`、`refactor:`、`style:`。
- `scope` 尽量对应实际模块，例如 `web-app`、`wechat-miniprogram`、`ui-design-preview`、`shared-assets`、`docs`。
- summary 可用中文或英文，但要清晰说明业务目的，并尽量与相邻历史风格保持一致。
- 不使用空泛描述，例如 `update`、`fix bug`、`调整代码`。
- WIP 只能在用户明确要求保存现场时使用，并写清阻塞点。

## 推送规则

每个 commit 成功后立即推送当前分支：

```bash
git push
```

如果推送失败：

- 不静默跳过。
- 先判断是网络、认证、远端拒绝还是需要拉取。
- 不在未确认情况下执行破坏性合并或 reset。
- 在最终反馈中说明失败原因和当前本地 commit 状态。

## 不应提交的情况

以下情况默认不提交：

- 用户只要求分析、讨论或制定方案，未产生文件改动。
- 改动尚未完成，明显无法验收。
- 测试或构建失败且不是用户明确要求保存现场。
- 无法区分本轮改动和已有旧改动。
- 发现真实密钥、密码、token、证书私钥进入 diff。
- 用户明确要求“先不要提交”。
