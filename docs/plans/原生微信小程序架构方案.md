# 原生微信小程序架构方案

> 状态：暂不作为当前主路线。自 2026-07-16 起，当前前端优先方案改为 `docs/plans/Web-App-模块规划.md`。

## 当前结论

- 当前主路线从 `uni-app` 切换为 **原生微信小程序**
- 当前阶段目标聚焦 **微信小程序单平台**
- 可视化教学核心优先围绕 **2D/3D 绘制与仿真能力** 设计

## 选择原生的原因

- 技术链更短，直接面向 `WXML + WXSS + JS + JSON`
- 对微信小程序原生能力的接入更直接，调试链路更清晰
- 对高频动画、手势交互、2D/3D 绘制场景更可控
- 后续自研教学可视化内核时，性能瓶颈更容易定位

## 总体目录建议

仓库根目录保持多模块，但微信小程序模块直接放在根目录：

- `wechat-miniprogram/`：原生微信小程序主模块
- `ui-design-preview/`：UI 设计与交互预览模块
- `docs/`：规划、方案、经验沉淀
- `shared-assets/`：跨模块共享品牌与公共资源
- `services/`：后续服务端模块
- `packages/`：后续公共模块

## 引擎分层

不建议从零做通用图形引擎，建议做 **教学可视化内核**。

### 1. 页面层

- 负责课程、实验入口、参数面板、结果展示
- 页面只做编排，不承载复杂渲染逻辑

### 2. 组件层

- 通用 UI：按钮、滑杆、表单、弹窗
- 教学 UI：坐标轴、图例、标注、公式卡片

### 3. 引擎核心层

- `Ticker`：时间推进
- `Scene`：场景管理
- `Node`：图元节点
- `Camera/ViewBox`：视口与坐标变换
- `EventSystem`：点击、拖拽、缩放、命中检测

### 4. 渲染层

- `canvas2d`：2D 主渲染路线
- `webgl`：未来 3D 渲染路线
- 渲染层不关心教学业务，只负责把场景状态画出来

### 5. 仿真层

- 负责物理或数学状态推进
- 对外只暴露统一的 `step(delta)`、`reset()`、`setParams()` 等接口

### 6. 教学场景层

- 抛体运动
- 斜面
- 单摆
- 弹簧振子
- 光路示意
- 电路连线

每个实验都是一个独立场景模块，不要把所有规则揉进一个大引擎。

## 学科扩展预留

- 当前 MVP 先从物理实验切入，但架构不要把内容模型写死在物理
- 后续需要能扩展到数学、化学，以及偏记忆教学的人文内容
- 渲染内核、交互系统、标注系统保持学科无关，学科差异主要落在场景配置、素材与教学流程
- 品牌与公共素材统一沉淀在仓库根目录 `shared-assets/`
- 公共资源目录规范见 `docs/plans/公共资源目录规范.md`
- 小程序信息架构与同步方案见 `docs/plans/小程序信息架构与本地优先同步方案.md`

## 2D / 3D 路线

### 第一阶段：只做 2D

优先使用：

- `canvas type="2d"` 做主要实验渲染
- 原生组件 + `WXS` 做部分高频交互辅助

适合先落：

- 坐标系
- 轨迹
- 受力分析
- 碰撞示意
- 函数图像

### 第二阶段：补图表与结构图

- 把图表、关系图、标注系统抽象为可复用模块
- 保持与实验场景解耦

### 第三阶段：再引入 3D

如确实需要 3D，再在引擎中补：

- `render/webgl`
- 3D 相机
- 3D 交互控制器
- 3D 场景模块

不要在第一阶段同时推进 2D 和 3D。

## 性能原则

- 每帧状态不要走大规模 `setData`
- 高频渲染数据尽量只保留在内存和 canvas 上下文中
- UI 与仿真层解耦，控制面板和实验渲染分开
- 大量计算预留到 `workers/`
- 每次只优化一个明确瓶颈：绘制、命中、动画、计算

## MVP 建议

第一期建议只做一个完整的 2D 物理实验链路：

1. 首页进入实验页
2. 实验页包含画布、参数面板、播放控制
3. 场景支持播放、暂停、重置、拖拽
4. 支持基础标注与结果展示

首个实验建议在以下三者中选一个：

- 抛体运动
- 斜面运动
- 单摆

## 对当前仓库的影响

- `wechat-miniprogram/` 作为原生微信小程序主工程
- 当前 `uni-app` 工程仅作为过渡参考，不再作为主线演进基础
- 后续如保留历史，可将现有方案归档说明，但不继续在其上扩展引擎能力
